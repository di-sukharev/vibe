# AGENTS.md

## Рабочие правила

- Пользователь принимает продуктовые решения. Ты отвечаешь за реализацию, качество и поддерживаемость как ведущий инженер.
- Опирайся на разговор и репозиторий. Самостоятельно исследуй, решай, реализуй, проверяй и сообщай результат в границах задачи. Соразмеряй усилия риску.
- Спрашивай только о нерешённом продуктовом выборе, данных для безопасного продолжения или неразрешённых разрушительных действиях, расходах и изменении доступа к данным. Уже полученный запрос или ответ — разрешение; не спрашивай повторно. Обычные инженерные решения принимай сам.
- Объясняй влияние на продукт, компромиссы и риски простыми словами. Давай технические детали по необходимости. Для действий пользователя указывай точные шаги и ожидаемый результат.
- Применяй принципы [ASD-STE100 Simplified Technical English](https://www.asd-ste100.org/about_STE.html) во всём общении и документации. Общайся на языке запроса пользователя. Документацию пиши по-русски. Используй короткие предложения, прямые формулировки и единые термины. Одно предложение — одна мысль или действие; один абзац — одна тема. Сокращай без потери смысла. Сохраняй команды и служебные идентификаторы.
- Следуй старшим инструкциям и текущему намерению пользователя. Общие правила храни здесь. `CLAUDE.md` импортирует их через `@AGENTS.md`; не дублируй текст.

## Контекст репозитория и продукта

- Перед незнакомой настройкой или продуктовой задачей прочитай `README.md`, `CHECKLIST.md` и нужную инструкцию. Используй уже прочитанный контекст. Проверяй код, скрипты, схемы и вывод программы.
- Ищи файлы через `rg --files` или неглубокое дерево, не через README. Используй инструменты, скрипты, генераторы и менеджер пакетов репозитория. Для JS в Codex предпочитай `PATH="/opt/homebrew/bin:$HOME/.bun/bin:$PATH"`.
- Сначала используй существующие утилиты, зависимости, API фреймворка и стандартную библиотеку. Для незнакомого API изучи `package.json`, локальные типы и примеры. При необходимости проверь официальную документацию. Новая рабочая или служебная зависимость требует явного разрешения; запрос с её названием достаточен.
- Храни объём продукта и постоянные решения в `CHECKLIST.md`. Неуказанная возможность — `absent`. Добавляй или возвращай `absent`/`removed` только по запросу, не по оставшемуся коду. Обновляй решения и реестр по ходу работы.
- Храни настройку, инфраструктуру и эксплуатацию в README/docs. Отражай существенные изменения поведения, контрактов и операций. Не дублируй списки из кода и не меняй документацию ради очевидных правок.

До работы прочитай инструкцию области:

| Область | Документ и правило |
| --- | --- |
| Границы модулей, инфраструктура | `docs/ARCHITECTURE.md` |
| Данные сайта, каталог, корзина, checkout, заказы, подписки, доступ, оплата | `docs/WEB_SURFACES.md`. Сохраняй владельцев поведения и один браузерный checkout. |
| Локальный PostgreSQL | `docs/LOCAL_DATABASE.md`, `docker-compose.yml`. Используй Docker Compose, если пользователь не выбрал другое. |
| Фоновая или периодическая работа | `docs/BACKGROUND_JOBS.md` |
| Настройка тестов, новые сценарии | `docs/TESTING.md`. Для mobile также прочитай мобильный README ветки `mobile`. |
| Деплой, облако, хранилище | `docs/DEPLOYMENT.md`, `infra/README.md`, инструкция выбранного провайдера/хранилища |

## Git и рабочие файлы

- До работы с веткой, коммитом, push или PR проверь `git remote -v` и `git status --short --branch`.
- Оставайся на текущей ветке, если пользователь не просил создать, сменить или переименовать её. Worktree, stage, commit, amend, rebase, reset и push требуют явного запроса. Никогда не используй `git stash`.
- Не добавляй в сообщения коммитов подписи AI-авторов: `Co-Authored-By` с моделью или агентом, `Generated with ...` и аналогичные приписки. Запрет действует для Claude, Codex и любых других AI-инструментов.
- Сохраняй чужую работу. Не перезаписывай, не форматируй и не очищай её без разрешения. Сообщай о блокировке чужими изменениями. Не очищай и не сбрасывай checkout ради продолжения.
- При установке отключи `origin` шаблона по README, кроме работы над самим шаблоном. Настраивай публикацию только по переданному адресу или запросу создания/публикации проекта. Не публикуй и не деплой новый проект случайно в репозиторий шаблона.
- Не копируй репозиторий. Изучай другие refs через `git show`, `git diff`, `git log`. Если checkout не позволяет проверить пакет/инструмент, создай пустой каталог только с нужной зависимостью. Удали его в рамках задачи.
- Временные файлы храни в `./.scratch/` или каталоге инструмента. Удали свои после работы, кроме нужных названному продолжению. Не удаляй файлы другой задачи.
- Убирай ненужные файлы своей задачи. До чужих удалений или широкой/разрушительной очистки спроси разрешение.
- Используй отдельные порты или настройки. Не останавливай процессы ради освобождения порта.
- Не включай секреты, ключи, cookies, данные клиентов и сырые `.env` в логи, примеры тестов, снимки, коммиты и ответы. Это относится и к tfvars/backend-конфигурации. Не ослабляй auth, права, валидацию, шифрование, лимиты и аудит.
- Меняй генерируемые файлы через исходник и генератор, если правила репозитория не требуют другого. Для Prisma меняй `schema.prisma` и генерируй миграции штатным способом. Ручной SQL миграций требует явного запроса. Дополнительные проверки и перенос данных размещай в ответственном backend или поддержанном процессе.

## Разработка

- Обзор и объяснение не меняют файлы без запроса на правки. Для правок без изменения поведения изучи код и соседние вызовы. Выполни дешёвые подходящие проверки; не добавляй тесты.
- Для существенного поведения определи результат и узкую проверку. Изучи путь от вызова до хранения и соседний код для поиска владельца и связанных рисков. Не обходи лишние слои.
- Для воспроизводимого дефекта сначала добавь падающий регрессионный тест, если инфраструктура позволяет. Иначе используй доступное воспроизведение и проверку. Сообщи о пробелах покрытия. Пересмотри причину, если повторные исправления не помогают.
- Исправляй причину у владельца, без дочерних подмен и повторных решений. Проверь затронутых вызывающих и потребителей даже при правке одного файла.
- Сохраняй продуктовый договор в текстах о праве, оплате, приватности, безопасности и поддержке. Разрешай смысловую неоднозначность до косметической правки.
- Делай минимальное целостное изменение с явным владельцем. Добавляй файлы, функции и абстракции только для текущей потребности. Малое дублирование лучше неверной абстракции. Убирай обходы, когда меняется владелец поведения.
- Для архитектуры и миграций объясняй совместимость, объём, риск и порядок внедрения.

Выбирай проверки по изменению:

| Изменение | Что проверить |
| --- | --- |
| Контракт/схема | Обе стороны: источник, потребитель, сериализация, чтение и запись |
| Auth/маршруты | Серверные права, guards, сессию и навигацию |
| Запросы | Ключи, сброс кэша, загрузку, ошибки и устаревшие данные |
| Асинхронная работа | Повторы, идемпотентность, порядок, отмену и видимость ошибки |

## Архитектура и интерфейс

- Следуй progressive DDD-lite; auth — образец backend/web. Контексты backend находятся в `backend/src/modules/<context>`. Связывай их публичными `index.ts` или application-портами. HTTP относится к transport, координация — к application, правила — к domain, Prisma/SDK — к infrastructure.
- Клиентские контексты находятся в `src/features/<context>`, общие возможности без endpoint — в `src/platform`. Маршруты/экраны составляют публичные API функций. Не прячь бизнес-правила в маршрутах, экранах, провайдерах или UI-примитивах.
- Предпочитай монолит и существующую инфраструктуру. Надёжная работа использует PostgreSQL outbox, периодическая — существующие jobs/schedules. Новую инфраструктуру добавляй для конкретной потребности. Записывай измеренные пределы и решения в `CHECKLIST.md`. Не добавляй пустые слои, generic/base repositories, CQRS и event sourcing для вида.
- Сохраняй визуальный язык без запроса на редизайн. Согласуй оформление с кодом, компонентами, стилями и заданными образцами.
- Общий компонент владеет поверхностью, отступами, скруглением, типографикой, элементами управления и внутренним расстоянием. Размещай его через обёртки и общую шкалу отступов; предпочитай padding/gap родителя. Сначала используй существующие смысловые props, затем новые переиспользуемые props или обёртку функции. Не переопределяй внутренности и не обходи примитив-владелец.

## Тестирование и проверка

- Выбирай самые узкие устойчивые проверки поведения и связанных рисков. Используй существующее покрытие. Добавляй тесты для значимого нового поведения или пропущенной регрессии. При необходимости сначала проверь исходное состояние. После правок повтори нужные проверки.
- Общую бизнес-логику проверяй преимущественно через реальное приложение/HTTP и изолированный тестовый PostgreSQL. Включай auth, права, хранение, валидацию, ошибки и границы. Не подменяй внутренние слои и БД. Внешних провайдеров можно контролировать для повторяемости. Unit — для чистых правил/клиента, contract — для общего формата API.
- E2E ограничен важными успешными путями через реальный клиент и backend: Playwright для web, Maestro для mobile. Новый путь нужен только там, где нижние уровни не доказывают связь клиента с сервером. По возможности расширяй существующий. Ошибки, границы и матрицы состояний проверяй ниже.
- В E2E проверяй результат: сохранение или переход, со стабильными test IDs/`testID`, независимыми от текста. Не проверяй оформление, макет, стили, формулировки и статический текст. Заменяй хрупкие утверждения проверкой поведения, не переноси косметику в другие тесты. Правка текста не должна ломать тесты.
- Для косметики достаточно обзора кода и локальных проверок. Браузер, его автоматизация/E2E, включая headless, и снимки требуют явного запроса. Визуальную проверку оставь пользователю без задержки завершения. Не выдавай невыполненную проверку за пройденную.
- Все проверки задачи выполняй локально. Не создавай и не используй GitHub Actions, GitHub CI/CD или облачные проверки. Полная регрессия нужна для явного релиза/аудита или сквозного изменения. Разрешённый production-релиз и пересборка SSG идут по инструкции деплоя отдельно от проверок задачи.
- При изменении границ зависимостей выполни `bun run architecture:check`. Для изменений Maestro, параметров его запуска или E2E-поведения mobile следуй мобильной инструкции и выполни `bun run --cwd mobile e2e:maestro:audit`.
- Проверка успешна только при верном поведении и чистом коде выхода. Сообщай ошибки, недоступные проверки и ограничения. Не объявляй завершение, пока основное поведение не работает.

## Деплой

- Следуй хостингу из `CHECKLIST.md` и его инструкции. При установке выбирай его по аудитории и размещению данных согласно README.
- Используй существующие Terraform-корни и `scripts/infra.mjs` для инфраструктуры и релизов.
- До облачных изменений проверь remote, рабочее дерево и ветку/коммит релиза. Остановись при грязном дереве, неопубликованном/рассинхронизированном исходнике или неясном источнике релиза.

## Отчёт о результате

- Кратко сообщи изменения, причины, проверки с результатами, риски и блокировки. При необходимости добавь первопричину, документацию, миграцию, внедрение и ограничения покрытия.
- Соразмеряй отчёт задаче. Не выводи пустые поля и лишние заголовки. Предложи короткое сообщение коммита для готовых изменений.
